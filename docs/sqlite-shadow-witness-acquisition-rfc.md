## Prospective observation records

Every record has a version, capture epoch and sequence, logical name and approved synthetic scratch root, capture method and provenance, explicit success/failure/unknown, receipt binding, and opaque byte count and SHA-256 where meaningful. The logical name is not a path identity. JSON records capture the exact source bytes before parsing, a separate optional parsed-value result, and source file identity. Artifact records capture each named object's bytes and identity independently; directories require a separately specified bounded enumeration and cannot be represented by a file digest alone. SQLite records identify the database and stage directory, logical state bytes and digest, store ID, generation and revision, and transaction/capture status. A raw database-file digest, if captured, is a separate physical observation and is not interchangeable with the state BLOB digest or a database snapshot. Absent, inaccessible, unsupported, ambiguous or inconsistent fields are unknown, never invented.

Prospective Windows identity is volume identity plus file ID obtained on the opened handle using `GetFileInformationByHandleEx(FileIdInfo)` (or an explicitly reviewed equivalent); record API, volume/filesystem, share flags and failure. IDs can be reused after deletion, have filesystem/network-specific support and lifetime limits, and do not prove path containment or authenticity. Capture reparse and link information and validate approved-root ancestry with reviewed handle-based native procedures; unresolved reparse points, aliases or unsupported semantics refuse. A simple string prefix, `stat`, or digest alone is insufficient. A scratch root must be independently approved and its identity recorded. No native implementation or environment admission is implied.

Mapping to existing code: `StagingReceipt:58` contains database path, store/project/schema IDs, generation, revision, source SHA and byte count, source path, source/directory/database identity tuples, and `advisory-before-and-after`; `StagedReadback:75` contains source bytes, model, revision, generation and SHA. `_validated_state:208` validates state and SQLite operation receipts; the latter bind operation ID, expected revision, replacement bytes/digest and resulting revision, not artifact witnesses. Reader `_stage_state:92` and `_source_signature:102` use stat-derived metadata; `_read_source` checks opened source bytes. Facade repeats reader observations. Explicit logical artifact records, trusted capture provenance, handle-based Windows volume/file IDs, approved-root identity, epoch, receipt version, independent authenticity and freshness evidence are **unimplemented additions**, not properties of the current receipt. A source digest is over bytes, not semantic JSON equality.

## Time, trust and consistency models

A prospective same-handle open, identify, read/hash, handle metadata check and re-read can bind returned bytes to that opened object at each read, and expose some changes while the handle stays open. Windows sharing modes may block some opens/replacement, depending on existing handles, flags and filesystem; they do not retroactively exclude already-open handles, all mutation, hardlink access, remote filesystem behavior or path substitution. A held handle may continue to name the old object after namespace replacement. Recheck the name with independently verified handle identity; this too is another observation, not an atomic compare-and-swap, and cannot prevent change immediately afterward or unobserved A-B-A. No claimed freeze follows from matching hashes, metadata or timestamps.

A SQLite read transaction may provide a consistent SQLite snapshot within that transaction subject to SQLite and filesystem semantics; it does not snapshot JSON or artifacts. Sidecars, journals, recovery, locks, native calls and durability are unresolved native boundaries: unexpected or unreviewed sidecars, busy status or uncertain recovery produce refusal, never cleanup. Stage CAS governs participating stage operations only. Direct JSON writers and CLI/edit routes do not thereby participate; the cooperative directory lock only covers its callers. Replacement after a check remains possible. A trustworthy cross-store temporal guarantee is impossible to establish with uncoordinated writers from these observations alone.

Compare three future models: (1) cooperative coordination could bound a guarantee only if every relevant JSON, stage and artifact writer obeys a verified common protocol for the full interval; nonparticipants are explicitly excluded and enforcement and crash recovery require separate proof. Existing locks do not establish this. (2) immutable/content-addressed versioned inputs could bind retained bytes to version names if immutability, publication, provenance and retention are independently enforced, including alias and replacement controls; a digest alone does not provide those properties. (3) observational-only records retain sampled evidence, refuse detected mismatches and mark continuous stability and cross-store simultaneity UNPROVEN. Choose (3) for this static gate: it makes no continuity or atomicity claim. Even an observed A-B-A refuses; equal endpoints cannot detect an unobserved A-B-A.

A proposed versioned receipt canonically binds root and logical names, source file identity and exact bytes/digest, stage directory/database identity and store/generation/revision/state digest, ordered artifact records, capture epoch and provenance, including failures. Its binding is a claim until an independently trusted collector and verifier establish origin and freshness. Hashing attacker-supplied fields, or `stage_verified=True`, authenticates nothing. A forged matching receipt, replay of a valid old epoch, ID reuse, clock rollback or copied content can mislead. Trusted keyed authentication or signatures and protected keys, a trusted monotonic counter or independently anchored freshness, and a verified collector may be necessary under the threat model; none exists here or is authorized. Without them refuse authenticity-sensitive use as UNPROVEN. No receipt establishes that nonparticipants were absent.

## Refusal, feasibility and next gate

The linked matrix specifies static prospective outcomes and retained evidence, not executable tests or runtime observations. Refusal preserves evidence and does not authorize deletion, repair, fallback or selecting a winner. Any unavailable capture, unresolved origin or uncertainty remains UNPROVEN.

The smallest separately authorizable prototype would observe one fabricated JSON file, one private synthetic stage and one fabricated regular artifact in an isolated approved scratch root, using a reviewed witness collector and no public route. Admission must first specify exact files and operations, native Windows API and filesystem/share/sidecar behavior, scratch containment, environment and process boundaries, and source review of every dependency. Objective positive checks must independently compare captured bytes, identities, receipt binding and stage revision on a quiescent fixture. Negative checks must demonstrate refusal for changed identity with same bytes, replacement, revision divergence, forged/replayed claims, observed ABA, unavailable identity, aliases, sidecar/busy and nonparticipant intervention; an unobserved ABA must remain UNPROVEN, not falsely pass as stable. Preserve raw independent observations, hashes, per-step process/admission/failure records and postpackage checks. Include interruption and durability as unknown unless separately admitted and proven. Prototype results cannot establish production safety or activate integration.

Historical record: R11 had eight unauthorized editing CLI dry-run starts; R14 ran 69/69 functional cases without completed prior safety review. Neither deviation is cured. R15's two busy-test cleanup edits remain applied but untested; R16B was not admitted and its review closed. R17 and R18 are static, untested and unintegrated. Native SQLite, Windows ACL/owner, hostile races, hardlinks, 3,102 historical directory records, Git provenance and crash/power-loss durability remain unproven. This RFC adds no runtime evidence and leaves P7 hold intact.
